The conversion flow

The one Terrence asked about. The account gate moves to the program-card click, upstream of the drawer opening, so the drawer's contents are behind it.

Three things the gate move breaks

  • The card never reopens after signup. applyIntent early-returns on /browse (PrototypeFrame.jsx:161) and there is no pending-action queue anywhere in the app. Needs one, or the person clicks the same card twice at peak intent.
  • The gate copy had to change, and did. It used to say nothing is withheld from someone who declines. Once it stands in front of the card, the card stays shut. Copy is now per-trigger, and the program variant's dismiss reads "Back to results".
  • The gate is now the thing that explains why. Brigid's point was that the program card never said the step was required to get the discount. The gate now carries that line, because it stands where that click was.

135 programs carry an applicationUrl. Three are real (apply.franklin.edu/?partnership=ALCA2 twice, mckendree.edu/apply); the other 132 are example.com. The Franklin partnership code is live-looking and should be verified before anything external.

directHandoff is implemented in one of three places

  • SNHU and Metro Tech are routingType: 'directHandoff' (schools.js:119, :135). The spec says they skip the chooser, the confirmation gate and the specialist step entirely.
  • AllyChat does that correctly (AllyChat.jsx:302) and links straight out.
  • The primary CTA does not. CtaFlow never reads routingType, so "Get program details" on an SNHU program opens the full four-option chooser including the gate. Exactly what the spec says to skip.
  • Nothing anywhere states what a directHandoff click should write to the CRM. The HubSpot table is implicitly standard-schools-only. That is a decision, not a bug.
